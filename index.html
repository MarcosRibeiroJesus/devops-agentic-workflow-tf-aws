Workflow tradicional vs. agêntico Arquitetura do projeto
O problema, e a virada

Do workflow tradicional ao agêntico

Hoje, o maior problema no fluxo de trabalho tradicional de um engenheiro DevOps sem agentes de IA é que a maior parte do tempo não é gasta em decisões arquiteturais ou de segurança, mas sim em tarefas repetitivas e manuais de digitação e correção.

ÁreaTradicional (sem IA)Com IA

TestesTestes roteirizados, cobertura limitada, casos instáveisIA gera casos de teste, detecta padrões instáveis, melhora a cobertura
Monitoramento e incidentesAlertas reativos, dashboards cheios de ruídoAnálise preditiva, detecção de anomalias, sugestão automática de causa raiz
Gestão de infraestruturaEscalonamento manual, recursos superprovisionadosEscalonamento preditivo, dimensionamento certeiro, otimização de custo

Segurança e complianceVarredura lenta, checagem manual de complianceIA varre o código, detecta ameaças e aplica políticas de compliance

01 · Fundamentos

O fluxo do DevOps, com e sem subagents

Revisar uma política de IAM antes do apply: dentro da conversa principal, ou isolado?

Sem subagents

  • A revisão de IAM roda na mesma janela de contexto da conversa principal
  • Cada arquivo revisado, um por um, consome espaço de contexto que não volta
  • O processo que revisa tem acesso às mesmas ferramentas que o resto, inclusive Write e Bash

Com subagents

  • terraform-reviewer roda isolado, com contexto próprio, sem contaminar a conversa principal
  • Só o resumo final volta pra você, o processo intermediário fica de fora
  • Ferramentas restritas a Read, Grep e Glob, reduzindo o raio de ação possível
  • Vários subagents podem revisar em paralelo, terminando no tempo do mais lento, não na soma

01 · Fundamentos

Hooks (conceito)

Disparado automaticamente em eventos do ciclo de vida do agente, sem precisar de um prompt pedindo isso.

Automação determinística, amarrada a um evento, não a uma instrução.

Analogia

É como um hook de pre-commit ou um gate de pipeline: dispara sozinho toda vez que o evento acontece, sem depender de alguém lembrar de rodar aquilo manualmente.

PreToolUse
evento: antes do Bash
dispara sozinho
Permite, bloqueia ou roda script
01 · Fundamentos

O fluxo do DevOps, com e sem Hooks

Impedir um terraform destroy acidental: pedir educadamente, ou bloquear de verdade?

Sem hooks

  • A única barreira é a instrução escrita no CLAUDE.md: contexto, não aplicação
  • Numa conversa muito longa, essa instrução pode ser esquecida ou mal interpretada
  • Um comando destrutivo só é percebido depois de já ter rodado

Com hooks

  • PreToolUse intercepta a chamada antes de executar, dentro do próprio harness
  • Retorna deny para comandos como terraform destroy: o agente não consegue rodar, ponto final
  • A checagem é código determinístico, não uma sugestão que o modelo decide seguir ou não
01 · Fundamentos

Rules x Hooks: contexto que orienta, execução que bloqueia

As duas reagem a um evento, mas uma é lida pelo modelo, a outra é aplicada pelo harness.

RulesHooks
CamadaContexto (soft)Execução do harness (hard)
Quando entraSempre, ou quando um path bateEm eventos específicos do ciclo de vida
Bloqueia de verdade?Não, é orientaçãoSim, retorna deny antes da execução
Exemplo"toda IAM policy declara recursos explicitamente"bloquear terraform destroy no PreToolUse
Analogia

É a diferença entre o guia de estilo de commits do time, que todo mundo tenta seguir (rule), e o hook de pre-commit que recusa o commit se o padrão não bater, e ninguém consegue burlar (hook).

01 · Fundamentos

O harness: como as peças viram um agente

CLAUDE.md, Skills, Agents, Rules, Hooks, MCP e Memória não competem entre si. Juntos, formam o harness.

O harness é a camada de contexto, limites e ferramentas construída ao redor do modelo bruto.

Importa sem harness, o modelo esquece tudo entre sessões e não tem limites.
Analogia

É a esteira de CI/CD ao redor de um script: sozinho, o script não sabe onde rodar, quem aprova ou o que é permitido. É o pipeline com suas etapas e guardrails que torna o processo confiável.

01 · Fundamentos

O fluxo do DevOps, com e sem memória entre sessões

O bucket de teste sempre precisa da tag Environment=workshop. Alguém tem que lembrar disso.

Sem memória entre sessões

  • Toda sessão nova esquece o padrão aprendido na sessão anterior
  • O mesmo erro é corrigido manualmente, de novo, toda vez que aparece
  • Só existe conhecimento acumulado se alguém escrever isso à mão no CLAUDE.md

Com Auto Memory

  • O padrão aprendido numa correção gruda sozinho para a próxima sessão
  • Fica registrado em ~/.claude/projects/.../memory/, sem editar nada manualmente
  • Só as primeiras 200 linhas (ou 25KB) do índice carregam sempre, o resto é sob demanda

01 · Fundamentos

O fluxo do DevOps, com e sem MCP

Antes de criar um bucket, o Claude sabe se ele já existe, ou descobre no meio do apply?

Sem MCP

  • O Claude não tem acesso direto ao estado real da conta AWS
  • Pode assumir, e errar, sobre limites de serviço, buckets existentes, distribuições já criadas
  • Abrir um PR no GitHub exige sair do fluxo e fazer manualmente

Com MCP

  • Um servidor MCP da AWS deixa o Claude consultar o estado real antes de agir
  • Evita alucinar sobre a infraestrutura: ele consulta, em vez de assumir
  • Um servidor MCP do GitHub abre o PR automaticamente, mantendo aprovação humana no fluxo

Hooks

Automação determinística em pontos do ciclo de vida do agente.

.claude/settings.json · exemplos de hooks para DevOps
// 1. Bloquear comando destrutivo antes de rodar
"PreToolUse": { matcher: "Bash(terraform destroy*)", command: "deny" }

// 2. Formatar automaticamente depois de editar .tf
"PostToolUse": { matcher: "Edit(*.tf)", command: "terraform fmt" }

// 3. Validar credenciais AWS antes de começar a sessão
"SessionStart": { command: "check-aws-profile.sh" }
02 · Segurança

Permissions

O que o agente pode, não pode, ou precisa perguntar.

.claude/settings.json
{
  "permissions": {
    "allow": ["Bash(terraform plan)", "Read(./infra/**)"],
    "ask":   ["Bash(terraform apply)"],
    "deny":  ["Bash(terraform destroy *)", "Bash(aws iam create-user *)"]
  }
}

O fluxo de trabalho, com e sem skills

A mesma tarefa de deploy, duas formas bem diferentes de chegar lá.

Sem skills

  • Você reexplica o contexto e os passos a cada pedido
  • A ordem dos passos muda dependendo de como você escreveu o prompt
  • Fácil pular uma etapa de segurança sem perceber
  • Resultado varia conforme quem chamou e como chamou

Com skills

  • Passo a passo gravado uma vez em SKILL.md, reaproveitado sempre
  • Mesma sequência sempre: /scaffold-terraform → /tf-plan → /tf-apply → /deploy
  • disable-model-invocation trava a etapa arriscada pro humano decidir
  • Resultado previsível, não importa quem chamou o comando
04 · Demonstração

Anatomia de um SKILL.md

Todo campo do frontmatter é opcional. Só description é recomendado, sem ele o Claude não sabe quando usar a skill sozinho.

.claude/skills/minha-skill/SKILL.md · vazio, com todos os campos
---
name: minha-skill # nome exibido (padrão: nome da pasta)
description: ... # o que faz e quando usar · recomendado
when_to_use: ... # contexto extra pra Claude acionar sozinho
argument-hint: [arg] # dica de autocomplete
arguments: [a, b] # nomeia argumentos pra $a, $b
disable-model-invocation: false # true = só manual, via /nome
user-invocable: true # false = só o Claude aciona
allowed-tools: Bash Read # libera ferramentas nesse turno
disallowed-tools: ... # remove ferramentas nesse turno
model: inherit # troca o modelo só nesse turno
effort: medium # troca o nível de raciocínio
context: fork # roda em subagente isolado
agent: general-purpose # qual subagente, com context: fork
background: true # roda o fork em segundo plano
hooks: {} # hooks registrados ao invocar
paths: ["infra/**"] # auto-ativa só nesses arquivos
shell: bash # bash (padrão) ou powershell
metadata: {} # dados livres pras suas ferramentas
license: MIT # licença da skill
compatibility: ... # requisitos de ambiente
---

scaffold-terraform: gera toda a infraestrutura

1 de 4 na esteira. .claude/skills/scaffold-terraform/SKILL.md

.claude/skills/scaffold-terraform/SKILL.md
---
name: scaffold-terraform
description: Generate complete Terraform infrastructure for S3 + CloudFront static site hosting. Use when setting up a new project or regenerating infrastructure files.
allowed-tools: Bash, Read, Write, Grep, Glob
disable-model-invocation: true
argument-hint: "[aws-region] [project-name]"
---

Generate a complete Terraform configuration for deploying a static website to AWS using S3 + CloudFront.

Use $ARGUMENTS for optional overrides:
- $0 = AWS region (default: ap-south-1)
- $1 = Project name (default: portfolio-site)

## What to Generate

Read template-spec.md in this skill folder for the full infrastructure specification.

Generate all files in the terraform/ directory following the template spec.

## After Generation

- [ ] List all files created
- [ ] Show a summary of resources that will be provisioned
- [ ] Remind the engineer to review the files and run /tf-plan when ready

scaffold-terraform: a especificação que ele segue

Arquivo de referência lido pela skill, não é um SKILL.md. .claude/skills/scaffold-terraform/template-spec.md

.claude/skills/scaffold-terraform/template-spec.md
# Terraform Template Specification

Generate these files in the terraform/ directory:

terraform/main.tf:
- S3 bucket (private, no public access, block all public ACLs)
- S3 bucket policy granting CloudFront OAC read access
- CloudFront Origin Access Control (OAC), NOT legacy OAI
- CloudFront distribution with: S3 origin using OAC · default root object index.html · custom error 404 → /index.html (200) · viewer protocol redirect-to-https · price class PriceClass_200 · cache behavior CachingOptimized
- All resources tagged with Project and Environment variables

terraform/variables.tf:
- Variables for: region, project_name, environment (default "production"), domain_name (default "")

terraform/outputs.tf:
- Outputs for: cloudfront_distribution_id, cloudfront_domain_name, s3_bucket_name, s3_bucket_arn

terraform/providers.tf:
- AWS provider with region variable, terraform block with required_version >= 1.5 and AWS provider source

terraform/backend.tf:
- S3 backend block (comentado, com instruções para descomentar depois de criar o bucket de state)
- Comentários explicando: primeiro terraform init sem backend, criar os recursos, depois descomentar e rodar terraform init -migrate-state

.claude/skills/tf-plan/SKILL.md
---
name: tf-plan
description: Run terraform plan and analyze the output for risks. Use before applying any infrastructure changes.
allowed-tools: Bash, Read, Grep
disable-model-invocation: true
---

Run cd terraform && terraform plan -no-color and analyze the output.

Summarize:
- [ ] How many resources will be added, changed, or destroyed
- [ ] Any potential issues or risks (e.g., resource replacements, security group changes, data loss)
- [ ] Estimated blast radius

If the plan fails, diagnose the error and suggest a fix.

---
name: tf-apply
description: Run terraform apply to create or update AWS infrastructure. Use after reviewing a terraform plan.
allowed-tools: Bash, Read
disable-model-invocation: true
---

Run cd terraform && terraform apply -auto-approve -no-color and verify the results.

After apply completes:
- [ ] Show the key outputs (CloudFront URL, S3 bucket name, distribution ID)
- [ ] Verify the deployment by checking if the CloudFront distribution status is "Deployed"
- [ ] Report any errors and suggest fixes

If apply fails, do NOT retry automatically. Show the error and wait for instructions.

deploy: publica o site

4 de 4 na esteira. .claude/skills/deploy/SKILL.md

.claude/skills/deploy/SKILL.md
---
name: deploy
description: Sync site files to S3 and invalidate CloudFront cache. Use after terraform apply to push site content live.
allowed-tools: Bash, Read
disable-model-invocation: true
---

Deploy site files to S3 and invalidate CloudFront cache.

Steps:
- [ ] Get terraform outputs: terraform output -json
- [ ] Sync site files: aws s3 sync . s3://<bucket> --exclude "terraform/*" ... --delete
- [ ] Invalidate cache: aws cloudfront create-invalidation --distribution-id <dist-id> --paths "/*"
- [ ] Report the CloudFront URL and invalidation status

If any step fails, stop and report the error. Do not continue.
